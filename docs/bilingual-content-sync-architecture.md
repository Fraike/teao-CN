# TEAO 中英文双站内容同步架构建议

整理日期：2026-06-10  
背景：英文国际站和中文独立站分别部署在不同服务器，但产品、文章、媒体和基础资料希望尽量一致，避免重复维护。

## 1. 结论

不要做两个完全独立后台。

建议做成：

> 一个内容管理中心 + 两个独立前台站点

也就是：

- 产品、文章、分类、媒体、SEO、客户案例在一个后台维护。
- 英文站和中文站分别部署在各自服务器。
- 两个站从同一套内容源读取或同步内容。
- 产品参数、图片、视频、型号等“事实数据”保持一致。
- 标题、描述、SEO、应用文案、文章正文按语言分别维护。

这样后面发产品、发文章时，不需要在两个后台重复录入。

补充结论：如果中文站部署在中国大陆服务器，英文站部署在美国服务器，最稳妥的方式不是让两个站实时共用一个远程数据库，而是：

> 一个统一后台负责编辑和发布，中文站、英文站各自保存一份已发布内容副本，并从本地读取。

也就是“统一写入，双站本地读取”。这样既能保证内容一致，也能保证中文站的国内访问速度、百度抓取稳定性和英文站的海外访问速度。

页面展示形式可以不同：

- 中文站可以更紧凑，更强调厂家实力、电话、微信、图纸询盘、国内应用案例。
- 英文站可以保持国际 B2B 风格，更强调 OEM、Tier-1、工程能力、全球供应。

但底层内容 ID 和事实数据必须一致：

- 同一个产品使用同一个产品 ID。
- 同一个型号只维护一份基础参数。
- 同一组图片、尺寸图、曲线图、视频只维护一份媒体记录。
- 同一篇文章主题使用同一个主题 ID，再分别维护中文版本和英文版本。
- 两个站可以有不同 URL、不同标题、不同页面布局，但不能让产品参数和媒体各自分叉。

## 2. 为什么不能简单做两个后台

如果英文站和中文站各有一个后台，会出现这些问题：

- 产品型号容易不一致。
- 参数、尺寸图、曲线图更新容易漏掉一边。
- 图片视频重复上传，占空间，也难管理。
- 中文文章和英文文章无法建立对应关系。
- 产品下架、分类调整、SEO 修改需要操作两次。
- 后期很难判断哪个站的数据是最新版本。

对于 TEAO 这种产品参数、图片、视频、认证和应用场景都比较多的网站，后期维护成本会很高。

## 3. 推荐方案：中心化内容后台 + 双站发布

### 3.1 架构说明

推荐架构：

```text
统一内容后台 / CMS
  ├─ 产品基础数据
  ├─ 中文内容
  ├─ 英文内容
  ├─ 新闻文章
  ├─ 媒体库
  ├─ SEO 信息
  └─ 发布状态

英文站服务器
  └─ teao-damper.com

中文站服务器
  └─ www.chinateao.com
```

内容发布流程：

```text
后台创建/修改内容
      ↓
保存产品基础数据
      ↓
分别填写中文/英文内容
      ↓
发布中文或英文
      ↓
触发英文站/中文站刷新
      ↓
两个站展示最新内容
```

### 3.2 核心原则

- 产品基础数据只维护一次。
- 中英文文案分别维护。
- 中英文 URL 可以不同。
- 中英文 SEO 可以不同。
- 媒体资源共用一套。
- 发布状态按语言控制。
- 每次发布都记录更新时间和版本。
- 前台服务器尽量读取本地已发布副本，不依赖跨境实时数据库查询。
- 后台发布时再触发同步，前台访问时不做跨境等待。

## 4. 内容模型建议

### 4.1 产品基础数据

这些字段中英文站应该共用：

- 型号
- 产品分类
- 子类型
- 扭矩范围
- 力值范围
- 阻尼方向
- 安装方式
- 材料
- 技术参数
- 尺寸图
- 性能曲线
- 产品图片
- 应用视频
- 排序
- 是否启用

这些属于事实数据，不应该中英文各维护一份。

### 4.2 产品语言内容

这些字段按语言维护：

- 产品名称
- 产品摘要
- 产品描述
- 特性卖点
- 应用场景说明
- SEO 标题
- SEO 描述
- 关键词
- URL slug
- FAQ
- 选型说明

示例：

```text
产品基础：
  model: RD-T015
  category: gear-damper
  torque: 50-500 gf.cm
  images: [...]

英文内容：
  name: RD-T015 Rotary Gear Damper
  slug: rd-t015
  seoTitle: ...

中文内容：
  name: RD-T015 齿轮阻尼器
  slug: rd-t015-gear-damper
  seoTitle: RD-T015 齿轮阻尼器_旋转阻尼器厂家
```

### 4.3 文章内容

文章也建议做“同一主题，不同语言版本”。

需要有一个 `translationGroupId` 或 `canonicalTopicId`：

```text
文章主题：
  topicId: automotive-interior-damper-guide

英文文章：
  title: Automotive Interior Dampers: Applications and Selection Guide
  locale: en
  slug: automotive-interior-dampers-applications-selection-guide

中文文章：
  title: 汽车内饰阻尼器应用与选型指南
  locale: zh-CN
  slug: automotive-interior-damper-guide-cn
```

这样可以知道两篇文章是同一个主题，但不是强行逐字同步。

中文文章要适合百度和国内客户阅读，英文文章要适合海外 Google/GEO 和国际客户阅读。

## 5. 三种技术实现方案

### 方案 A：两个站共用一个数据库

方式：

- 英文站和中文站都连接同一个远程数据库。
- 一个后台写入数据库。
- 两个站直接读取同一份数据。

优点：

- 实现简单。
- 数据天然一致。
- 不需要额外同步逻辑。

缺点：

- 两台服务器都依赖同一个数据库网络。
- 如果中文服务器在国内，跨境访问数据库可能慢或不稳定。
- 数据库故障会同时影响两个站。
- 权限和安全边界要更谨慎。

适合：

- 两个服务器网络都很稳定。
- 数据库放在两边都能稳定访问的位置。
- 前期想快速上线。

### 方案 B：中心 CMS/API，两个站读取并缓存

方式：

- 建一个统一内容后台和 API。
- 英文站、中文站通过 API 获取内容。
- 前台页面使用缓存、ISR 或构建时生成。
- 发布后通过 webhook 通知对应站点刷新页面。

优点：

- 后台统一。
- 两个前台保持独立部署。
- 前台访问速度可以靠缓存保证。
- 可以按语言分别发布。
- 后期扩展到更多语言更容易。

缺点：

- 要做 API 权限、缓存刷新、发布流程。
- 如果 API 不稳定，未缓存内容可能受影响。

适合：

- TEAO 当前这种双站长期维护。
- 产品和文章会持续更新。
- 希望后台只录入一次。

这是我最推荐的方案。

### 方案 C：中心后台 + 双站本地数据库同步

方式：

- 后台仍然只有一个。
- 英文站、中文站各有自己的本地数据库。
- 每次发布内容后，把数据同步到对应站点数据库。
- 两个站前台只读本地数据库。

优点：

- 中文站访问速度和稳定性最好。
- 即使中心后台短暂不可用，前台不受影响。
- 适合国内服务器和海外服务器网络不稳定的情况。
- 可以做发布记录、失败重试、同步状态。

缺点：

- 开发复杂度最高。
- 要处理同步失败、版本冲突、回滚。
- 要做同步日志和监控。

适合：

- 中文站部署在中国大陆。
- 海外服务器和国内服务器互访不稳定。
- 对前台稳定性要求高。

对于当前 TEAO 的情况，这个方案应作为优先方案：

- 中文站服务器在国内，更适合国内访问、百度抓取和国内客户打开速度。
- 英文站服务器在美国，更适合海外客户访问。
- 统一后台可以部署在国内、美国或单独服务器，但发布后的内容要同步到两个站各自本地。
- 前台展示不需要一致，数据源和发布版本需要一致。

推荐读取方式：

```text
统一后台 / 主数据
      ↓ 发布
同步到中文站本地库 / 本地缓存
      ↓
www.chinateao.com 从国内服务器本地读取

统一后台 / 主数据
      ↓ 发布
同步到英文站本地库 / 本地缓存
      ↓
teao-damper.com 从美国服务器本地读取
```

这样中文站访问不会被美国服务器拖慢，英文站访问也不会被国内服务器拖慢。

## 6. 推荐落地路线

我建议分两步走。

### 第一阶段：先做统一后台和内容模型

先不要急着做复杂同步。

要先把内容模型改对：

- 产品基础表。
- 产品多语言表。
- 分类基础表。
- 分类多语言表。
- 文章主题表。
- 文章多语言表。
- 媒体表。
- 发布状态表。

后台支持：

- 产品基础信息只填一次。
- 中文内容和英文内容分 Tab 编辑。
- 中文可单独发布。
- 英文可单独发布。
- 发布后显示哪个站已更新。

### 第二阶段：根据服务器情况选发布方式

如果两台服务器都能稳定访问同一个 API：

- 用方案 B。
- 两个站通过 API + 缓存读取内容。
- 发布后 webhook 刷新页面。

如果中文站在大陆、跨境网络不稳定：

- 用方案 C。
- 后台发布后同步数据到中文站本地数据库。
- 中文站前台只读本地数据库。

结合你现在的服务器规划，建议直接按方案 C 设计，但第一版实现可以做轻量：

- 后台保存主数据。
- 发布时生成标准 JSON payload。
- 中文站接收中文已发布内容并写入本地库。
- 英文站接收英文已发布内容并写入本地库。
- 两个站前台只读各自本地库。
- 同步失败时后台显示失败状态，并允许手动重试。

这样后续即使服务器、CDN、数据库迁移，内容架构也不用推倒重来。

## 7. 媒体资源怎么同步

产品图片、尺寸图、曲线图、视频不要分别上传到两台服务器。

建议做统一媒体库：

- 图片、视频上传到对象存储。
- 数据库只保存媒体 URL、alt、标题、用途、语言说明。
- 两个站引用同一套媒体。
- 如果中文站在大陆，可以给媒体接国内 CDN。
- 如果英文站面对海外客户，可以给同一套资源配置海外 CDN 或镜像 CDN。

媒体字段建议：

- 文件 URL
- 文件类型
- 产品关联
- 分类关联
- 中文 alt
- 英文 alt
- 是否可公开
- 是否需要下载保护
- 上传时间
- 使用页面

产品图片和视频仍要保留普通用户下载摩擦，例如禁止明显下载入口、图片不可拖拽、视频不显示下载按钮。

## 8. 发布流程建议

### 8.1 发产品

建议流程：

1. 后台新增产品基础信息。
2. 上传产品图、尺寸图、性能曲线、视频。
3. 填英文产品内容。
4. 填中文产品内容。
5. 选择发布到英文站、中文站，或两个站都发布。
6. 系统检查必填项。
7. 发布并刷新对应站点。
8. 记录发布日志。

产品可以允许这种状态：

- 只发布英文。
- 只发布中文。
- 中英文都发布。
- 基础数据已录入，但某语言未完成。

### 8.2 发文章

建议流程：

1. 创建文章主题。
2. 选择文章类型：新闻、技术文章、应用指南、公司动态。
3. 写英文版本。
4. 写中文版本。
5. 关联产品和应用。
6. 分别设置中英文 SEO。
7. 分别发布。

注意：文章不建议机械翻译后直接同步。中文文章应该针对百度和国内客户重写标题、摘要、关键词和结构。

### 8.3 同步状态

后台最好显示：

- 英文站发布时间。
- 中文站发布时间。
- 英文站同步状态。
- 中文站同步状态。
- 最后同步错误。
- 手动重新同步按钮。

## 9. 内容一致性怎么保证

### 9.1 必须一致的内容

这些要从同一份基础数据读取：

- 型号
- 产品参数
- 扭矩范围
- 尺寸图
- 性能曲线
- 材料
- 阻尼方向
- 安装方式
- 产品图片
- 产品视频
- 是否启用

### 9.2 可以不同的内容

这些应该按语言和市场分别优化：

- 产品名称。
- 页面标题。
- SEO 描述。
- 产品摘要。
- 应用说明。
- 首页文案。
- 新闻标题。
- 技术文章结构。
- CTA。
- 联系方式。

中文站更强调：

- 源头厂家。
- 工厂实力。
- 打样定制。
- 电话/微信咨询。
- 国内应用案例。
- 百度关键词。

英文站更强调：

- OEM / Tier-1。
- Global supply。
- Engineering support。
- International B2B programs。
- Google/GEO 语义覆盖。

## 10. 英文发布后中文内容怎么处理

不建议英文后台发完后，中文站直接把英文内容机器翻译并自动上线。

更推荐的流程是：

> 英文发布后，中文自动生成待审核草稿；产品事实数据直接同步；中文文案经人工确认后再发布。

原因很简单：

- 产品参数、型号、图片、尺寸图、性能曲线必须完全一致，可以自动同步。
- 产品标题、摘要、卖点、SEO、FAQ 需要符合中文搜索和国内客户习惯，不能只机器翻译。
- 新闻和技术文章如果直接翻译，中文标题容易不适合百度收录，也不适合国内客户阅读。
- 国内站要加入电话、微信、图纸询盘、源头厂家、定制打样等表达，英文原文通常没有这些重点。

### 10.1 产品内容流程

产品最适合做“自动同步 + 中文草稿补全”。

发布英文产品时：

```text
英文后台发布产品
      ↓
产品基础数据自动同步到中文站
      ↓
系统生成中文产品草稿
      ↓
中文编辑确认产品名称、摘要、SEO、应用说明
      ↓
中文站发布
```

自动同步字段：

- 型号
- 分类
- 扭矩范围
- 力值范围
- 阻尼方向
- 安装方式
- 技术参数
- 材料
- 尺寸图
- 性能曲线
- 产品图片
- 产品视频
- 是否启用

自动生成中文草稿字段：

- 中文产品名
- 中文摘要
- 中文描述
- 中文 SEO 标题
- 中文 SEO 描述
- 中文 FAQ
- 中文应用说明

这些草稿可以由 AI 翻译/改写先生成，但必须标记为“待审核”，不能默认直接发布。

### 10.2 新闻和技术文章流程

新闻和文章更适合做“主题同步 + 中文本地化改写”。

发布英文文章时：

```text
英文文章发布
      ↓
创建同一主题的中文草稿
      ↓
AI 生成中文初稿
      ↓
人工调整标题、摘要、结构、关键词和 CTA
      ↓
中文站发布
```

中文文章不必和英文逐段一致，但主题、关联产品和核心事实要一致。

需要同步一致的内容：

- 文章主题
- 关联产品
- 主图
- 发布时间或事件时间
- 核心事实
- 可公开数据

可以中文本地化的内容：

- 标题
- 摘要
- 段落结构
- 关键词
- CTA
- 应用案例表达
- 国内客户关心的补充说明

### 10.3 后台状态设计

后台应显示每个内容的语言状态：

```text
英文：已发布
中文：待生成 / 待审核 / 已发布 / 需更新
```

当英文内容更新后，如果对应中文内容还没更新，后台应提示：

```text
英文版本已更新，中文版本可能需要同步检查。
```

建议状态：

- `draft`：草稿
- `machine_translated`：机器生成草稿
- `needs_review`：待人工审核
- `approved`：已审核
- `published`：已发布
- `outdated`：源语言已更新，需要复核

### 10.4 哪些可以自动发布，哪些不能

可以自动发布或自动同步：

- 产品基础参数
- 图片和视频关联
- 尺寸图
- 性能曲线
- 分类关联
- 排序
- 启用/停用状态

不建议自动发布：

- 中文产品标题
- 中文 SEO 标题和描述
- 中文新闻正文
- 中文技术文章
- 首页和落地页文案
- 涉及客户、认证、产能、质量承诺的内容

### 10.5 最推荐的实际操作方式

实际使用时可以这样：

1. 主要在英文后台录入产品和新闻。
2. 系统自动同步事实数据。
3. 系统自动生成中文草稿。
4. 中文编辑只需要审核和优化，不需要从零写。
5. 审核通过后发布到中文站。
6. 如果英文内容后续修改，中文版本标记为“需更新”，由人工确认是否同步。

## 11. URL 不要强行一致

两个站的 URL 可以不一样。

英文站继续保留已有产品 canonical 规则：

```text
/{category}/{slug}
```

中文站可以根据旧站 SEO 决定：

```text
/gear-damper/gear-rotary-damper-rd-t038-v038.html
```

或：

```text
/gear-damper/rd-t038
```

关键不是 URL 完全一致，而是同一个产品在后台有同一个产品 ID，然后分别生成英文 URL 和中文 URL。

## 12. 需要提前决定的几个问题

开工前需要确认：

- 统一后台放在哪台服务器，还是单独第三台服务器。
- 中文站服务器在大陆、香港还是海外。
- 两台服务器之间网络是否稳定。
- 媒体资源放哪里：本地服务器、阿里云 OSS、腾讯云 COS、Cloudflare R2 或其他对象存储。
- 是否需要国内 CDN。
- 是否保留现有英文站后台，还是升级成统一后台。
- 是否允许中文站直接访问英文站 API。
- 是否需要文章自动生成中文草稿，人工审核后发布。
- 是否需要产品自动同步到两个站，但文章手动选择同步。

## 13. 我的建议

最稳妥的路线：

1. 不做两个后台。
2. 以当前英文站后台为基础，升级成“多语言内容后台”。
3. 产品基础数据共用，中英文内容分开。
4. 媒体统一存储，不在两台服务器重复上传。
5. 初期用中心 API + 缓存。
6. 如果中文服务器在大陆且跨境不稳定，再增加“同步到中文站本地数据库”。
7. 发布时用 webhook 刷新两个站页面。
8. 后台显示每个站的同步状态和失败重试。

这样既能保持两个独立站部署，又能保证产品和文章从一个地方维护。

## 14. 后续开发任务拆分

如果采用推荐方案，后续开发可以拆成：

1. 设计多语言数据表。
2. 改造产品后台：基础信息 + 中英文内容 Tab。
3. 改造新闻后台：文章主题 + 中英文版本。
4. 改造媒体库：统一媒体、双语 alt、公开权限。
5. 增加发布状态和同步日志。
6. 增加内容 API。
7. 英文站改为从新内容模型读取。
8. 中文站从同一内容模型读取或同步。
9. 增加 webhook 页面刷新。
10. 增加失败重试和手动重新同步。

这部分应该先做数据库和后台，再做中文站前台。否则前台做完后还要大改内容结构。
